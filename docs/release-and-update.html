1Panel 发布与更新
总览 一次性准备 发版步骤 CI 流水线 产物与清单 客户端检查 弹窗规则 各系统安装 排查与限制

打包 · 发布 · 客户端更新流程说明

适用于 1Panel（Wails v3）的 macOS / Windows / Linux 三个平台。推一个 v* tag，GitHub Actions 会并行构建三个平台的安装包，统一上传到 GitHub Release（内部归档）和 S3 兼容对象存储（客户端更新源）。客户端定时检查签名清单，按版本策略弹出可选更新或强制更新。

macOS universal

  • 产物：1Panel-vX-mac-universal.zip
  • 构建机：macos-latest
  • 自动更新：支持

Windows amd64

  • 产物：1Panel-vX-win-amd64.zip
  • 构建机：windows-latest
  • 自动更新：支持（便携版）

Linux amd64

  • 产物：1Panel-vX-linux-amd64.tar.gz
  • 构建机：ubuntu-24.04
  • 自动更新：仅用户目录安装

1整体流程总览

从开发者推 tag 到用户完成更新的完整链路：

源码仓库 itjun/1Panel 是私有的，客户端拿不到它的 GitHub Release，所以更新包放在公开读取的 S3 兼容存储里（阿里云 OSS / 腾讯云 COS / Cloudflare R2 / MinIO 等）。GitHub Release 只做内部归档。

2一次性准备（只需做一次）

签名密钥

公钥内置在 internal/updater/pubkey.go。私钥以 scrypt + AES-256-GCM 加密后提交在仓库的 release/update_sign.key.enc，CI 用 Secret 里的口令解密后签名。明文私钥与口令只在本机 ~/.config/1panel-release/（权限 0600），.gitignore 会拦住明文私钥被误提交。把口令上传到 GitHub Secret：

gh secret set UPDATE_KEY_PASSPHRASE -R itjun/1Panel < ~/.config/1panel-release/passphrase
口令务必另外备份（如密码管理器）。仓库里只有密文，丢了口令等于丢了私钥：已安装的客户端将无法验签新清单，只能让所有用户手动重装一个内置新公钥的版本。口令一旦泄露，任何能读仓库的人都能签发更新，需立即换钥。
# 换口令：用新口令重新加密，再更新 Secret
UPDATE_KEY_PASSPHRASE='新口令' go run ./cmd/releasetool encrypt-key \
  -in ~/.config/1panel-release/update_sign.key -out release/update_sign.key.enc

GitHub 仓库配置（Settings → Secrets and variables → Actions）

名称类型说明
UPDATE_KEY_PASSPHRASESecret解密 release/update_sign.key.enc 的口令
S3_ENDPOINTSecretS3 兼容端点，如 https://oss-cn-hangzhou.aliyuncs.com
S3_BUCKETSecret存储桶名
S3_ACCESS_KEY_ID / S3_SECRET_ACCESS_KEYSecret有写权限的访问密钥
S3_REGIONSecret（可选）默认 auto
UPDATE_BASE_URLVariable客户端读取的公开 HTTPS 地址，构建时注入程序，例如 https://dl.example.com/1panel
S3_PREFIXVariable（可选）桶内目录前缀，需与 UPDATE_BASE_URL 对应
S3_ADDRESSING_STYLEVariable（可选）阿里云 OSS 设为 virtual

未配置 UPDATE_BASE_URL 或 UPDATE_KEY_PASSPHRASE 时，CI 跳过清单和上传，照常发 GitHub Release；客户端显示「此构建未配置更新源」，不检查更新。

3每次发版的操作步骤

  1. 提交代码。如果改过 agent 源码，确认 internal/agentres/VERSION 和 SOURCE.sha256 已一起提交（本地 python build.py 会自动升号），否则 CI 第一步检查会失败。
  2. （需要强制更新时）修改 release/update-policy.json 的 minSupportedVersion，并提交。
  3. 打附注 tag 并推送，tag 说明就是客户端弹窗里的更新说明。
  4. 等待 CI 完成（GitHub → Actions → Release），约 10–20 分钟。
  5. 客户端自动收到：下次启动后约 10 秒，或运行中下一个 6 小时检查周期。
# 可选：本版强制所有低于 v1.1.0 的客户端更新
echo '{ "minSupportedVersion": "v1.1.0" }' > release/update-policy.json
git commit -am "chore: v1.1.0 强制更新"

# 附注 tag：说明文字会显示在客户端更新弹窗
git tag -a v1.1.0 -m "v1.1.0 更新说明
- 新增应用内自动更新
- 修复若干问题"
git push origin main v1.1.0
三个平台必须各自在对应系统的构建机上编译（Wails 依赖 CGO 和各平台原生 WebView：WebKit / WebView2 / WebKitGTK），但这由 CI 矩阵并行完成，开发者只需推一个 tag，不需要分别在三台电脑上发布。

4CI 流水线详解（.github/workflows/release.yml）

flowchart TB t["push tag v*"] --> e1 subgraph job1 [Job embedded on ubuntu-latest] e1["agentversion check 版本号已提交?"] -->|否| fail1["失败 终止发版"] e1 -->|是| e2["task agent:build 编 agent amd64/arm64"] e2 --> e3["iperf:fetch 下载并校验 iperf3"] e3 --> e4["上传 artifact embedded-bin"] end e4 --> m1 e4 --> w1 e4 --> l1 subgraph job2 [Job build 矩阵并行] m1["macOS: 还原内嵌产物"] --> m2["task darwin:package:universal"] --> m3["zip -r -y 1Panel.app"] w1["Windows: 还原内嵌产物"] --> w2["task windows:build"] --> w3["7z 打包 1Panel.exe"] l1["Linux: 还原内嵌产物 + apt 装 GTK4/WebKitGTK"] --> l2["task linux:build"] --> l3["tar.gz 二进制 + desktop + 图标"] end m3 --> r1 w3 --> r1 l3 --> r1 subgraph job3 [Job release on ubuntu-latest] r1["下载三个产物"] --> r2["发布 GitHub Release"] r2 --> r3{"配置了 UPDATE_BASE_URL 和 UPDATE_KEY_PASSPHRASE?"} r3 -->|否| skip["跳过更新源上传"] r3 -->|是| r4["releasetool manifest 计算 sha256 生成 latest.json"] r4 --> r5["口令解密仓库内私钥 releasetool sign → latest.json.sig"] r5 --> r6["releasetool verify 用内置公钥复核"] r6 --> r7["aws s3 cp 先传安装包"] r7 --> r8["最后覆盖 latest.json 与 .sig"] end
环节要点
版本号注入三个平台的 Taskfile 都以 -ldflags -X main.buildVersion=$(git describe --tags) 写入版本，-X main.updateBaseURL 写入更新源地址。
内嵌产物spanel-agent 与 iperf3 被 gitignore，统一在 Linux 上构建一次再分发，三个包内嵌版本一致；不依赖 Windows 上的 shell 工具。
上传顺序先传 vX/ 下的安装包（长缓存），最后覆盖根目录清单（no-cache, max-age=60），客户端读到新清单时安装包一定已就绪。
签名复核上传前用客户端内置公钥再校验一次，防止 Secret 里的私钥与代码中的公钥不配对。

三重安全校验

flowchart LR a["下载 latest.json + .sig"] --> b{"ed25519 验签 内置公钥"} b -->|失败| x["丢弃 不写缓存"] b -->|通过| c["读取安装包 url / sha256 / size"] c --> d["下载安装包"] d --> e{"大小与 sha256 一致?"} e -->|否| y["删除文件 报错 可重试"] e -->|是| f["进入安装替换"]

即使存储桶或 CDN 被篡改，没有私钥也无法伪造清单，篡改后的安装包也过不了 sha256 校验。

6客户端检查更新流程

flowchart TB start["应用启动 ApplicationStarted"] --> clean["清理上次更新残留 .old"] clean --> en{"构建配置了更新源 且平台支持?"} en -->|否| off["关于页显示原因 不检查"] en -->|是| cache{"本地有已验签的缓存清单?"} cache -->|有| ev1["用缓存判定 若强制则立即弹窗 断网也拦截"] cache -->|无| devq ev1 --> devq{"开发构建?"} devq -->|是| manual["只允许手动检查 永不强制"] devq -->|否| wait["等待 10 秒"] wait --> fetch["拉取 latest.json + .sig"] fetch --> ok{"成功且验签通过?"} ok -->|否| silent["静默失败 保留上次状态"] ok -->|是| save["写入缓存 比较版本"] save --> decide["进入弹窗规则判定"] silent --> sleep["每 6 小时 ±10 分钟"] decide --> sleep sleep --> fetch
触发方式行为
启动检查启动后约 10 秒检查一次。
定时检查应用运行期间每 6 小时检查一次，加 ±10 分钟随机抖动，避免所有客户端同时请求。
手动检查设置 → 关于 → 应用更新 →「检查更新」，结果显示在该行；发现新版本直接打开弹窗。
自动检查开关设置 → 关于 →「自动检查更新」。关闭后可选更新不再主动弹窗，但强制更新仍会检查和拦截。
开发构建版本形如 v1.0.3-396-g83ba46a（本地 build.py 产物）不自动检查、永不强制，手动检查可用。

7弹窗规则：强制更新与可选更新

flowchart TB v{"新版本 > 当前版本?"} -->|否| none["已是最新 不弹窗"] v -->|是| m{"当前版本 < minSupportedVersion?"} m -->|是| forced["强制更新弹窗 不可关闭"] m -->|否| a{"自动检查开关开启?"} a -->|否| none2["不主动弹窗 关于页显示有新版本"] a -->|是| s{"用户跳过了这个版本?"} s -->|是| none2 s -->|否| r{"在 24 小时稍后提醒期内?"} r -->|是| none2 r -->|否| opt["可选更新弹窗"] forced --> vis{"主窗口可见?"} opt --> vis vis -->|否| notify["额外发系统通知 点击回到应用并打开弹窗"]

可选更新 默认

  • 立即更新：下载 → 校验 → 替换 → 自动重启
  • 稍后提醒：24 小时内不再弹出该版本
  • 跳过此版本：该版本不再提醒，有更新版本时再弹
  • Esc / 点遮罩只关闭本次弹窗，6 小时后的检查会再次提醒

强制更新 必须更新

  • 触发：当前版本低于清单里的 minSupportedVersion
  • 弹窗不可关闭，Esc 与点遮罩无效
  • 只有立即更新和退出应用两个按钮
  • 不受自动检查开关影响；断网时用缓存清单继续拦截

8各操作系统的下载安装与重启

三个平台共用「下载到 ServerPanel/update/download/ → 校验」流程，替换方式按平台区分。替换都采用「旧件改名为 .old → 新件挪入原位 → 失败则改回」，保证任何一步失败都不会留下损坏的应用。

macOS

flowchart LR z["下载 .zip 校验通过"] --> d["在 .app 同目录建临时目录"] d -->|无写权限| adm["系统授权框 管理员身份替换"] d --> u["ditto 解压 保留签名与符号链接"] u --> q["清除 quarantine 隔离属性"] q --> sw["1Panel.app → 1Panel.app.old 新包挪入原位"] adm --> rs sw --> rs["open 重新启动 /Applications/1Panel.app"] rs --> cl["新进程启动后删除 .app.old"]

Windows（便携版）

flowchart LR z["下载 .zip 校验通过"] --> x["解出 1Panel.exe → 1Panel.exe.new"] x --> sw["运行中的 1Panel.exe 改名为 .old"] sw --> mv[".new 改名为 1Panel.exe"] mv --> rs["拉起新 exe 旧进程退出"] rs --> cl["新进程等待 WebView2 释放锁 后台删除 .old"]

Linux

flowchart LR chk{"安装方式"} -->|"用户目录二进制 如 ~/.local/bin"| z["下载 .tar.gz 校验通过"] chk -->|AppImage| no1["提示到发布页下载新版"] chk -->|"deb / rpm 系统目录不可写"| no2["提示用包管理器或发布页更新"] z --> x["解出 1Panel → 1Panel.new"] x --> sw["旧二进制改名为 .old 新文件挪入原位"] sw --> rs["exec 重新启动"] rs --> cl["新进程启动后删除 .old"]
平台安装包内容替换对象限制
macOS1Panel.app正在运行的 .app（通常 /Applications）ad-hoc 签名、未公证；Go 下载的文件不带隔离属性，替换后可直接启动
Windows1Panel.exe正在运行的 exe 所在位置便携版；放在 Program Files 等需管理员权限的目录会替换失败
Linux1Panel + desktop + 图标正在运行的二进制只支持用户可写目录；AppImage、deb/rpm 需手动更新

9排查、本地联调与已知限制

本地联调（不发版测试更新流程）

# 1. 生成假版本清单并签名
go run ./cmd/releasetool manifest -version v9.9.9 -base-url http://127.0.0.1:18765 \
  -asset darwin-universal=/tmp/upd/v9.9.9/1Panel-v9.9.9-mac-universal.zip -out /tmp/upd/latest.json
go run ./cmd/releasetool sign -key-file ~/.config/1panel-release/update_sign.key \
  -in /tmp/upd/latest.json -out /tmp/upd/latest.json.sig

# 2. 起本地更新源
cd /tmp/upd && python3 -m http.server 18765

# 3. 指向本地源并伪装成旧版本启动（清单仍须通过内置公钥验签）
ONEPANEL_UPDATE_BASE_URL=http://127.0.0.1:18765 ONEPANEL_UPDATE_CURRENT_VERSION=v1.0.0 \
  /Applications/1Panel.app/Contents/MacOS/1Panel

常见问题

现象原因与处理
关于页显示「此构建未配置更新源」构建时没有 UPDATE_BASE_URL（本地 build.py 默认如此）。发布构建由 CI 注入。
关于页显示「开发构建无法比较版本」版本号不是合法 semver（如只有提交短 SHA），先打 tag 再构建。
CI 第一步「Check agent version committed」失败agent 源码改了但没提交新的 VERSION / SOURCE.sha256，本地跑 task agent:build 后提交。
CI「releasetool verify」失败口令错误（「无法解密私钥」），或 release/update_sign.key.enc 与 pubkey.go 中的公钥不配对。
客户端检查失败「清单签名校验失败」清单和签名不是同一次生成，或上传过程中只更新了其中一个；重新跑一次发版的上传步骤。
更新时提示「已取消管理员授权」macOS 的 .app 所在目录当前用户不可写，需要在授权框输入管理员密码。

已知限制

  • 首次上线：已安装的 v1.0.x 没有更新模块，需要手动安装一次带更新功能的版本，之后才能自动更新。
  • 强制更新依赖客户端至少成功拉取过一次清单（或已有缓存），从未联网成功的旧客户端拦截不到。
  • 更换签名密钥时，必须先发一个内置新公钥的版本，再改用新私钥签名。
  • Windows ARM、Linux ARM 暂无安装包。
